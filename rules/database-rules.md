# Database rules — the long statement

> **What this document is.** The reasoning behind the `N` rules that group R6 of the
> [catalogue](project-rules.md) indexes. Here they are argued; there they oblige.
>
> **It does not declare.** If this document and the catalogue disagree, the catalogue wins and this one
> is corrected in the same change (R0.1).
>
> The engine is **Oracle Database 23ai Free** ([ADR-001](../docs/adr/ADR-001-oracle-23ai.md)). Everything
> below assumes it, and several rules exist only because of it.

---

## N0 — The four principles

They resolve the cases no specific rule covers. They are not catalogue rows and never will be: something
applied by judgement is not stated as a checkable sentence.

**N0.1 — The database guarantees what cannot depend on somebody remembering.** Uniqueness, ranges,
mutual exclusion and referential integrity are declarations in the schema, not `if`s in a service. An
`if` runs in one request; a constraint runs in all of them, including the two that arrive at the same
millisecond.

**N0.2 — One concept, one representation.** The same thing is named the same way, stored in the same
type and with the same shape across the whole schema. Two spellings of one idea is the defect that
produces a query that silently returns less.

**N0.3 — What is queried gets indexed, and what is indexed gets queried.** An index that no query uses
is a tax on every write. A query with no index is a table scan that only hurts once there is data, which
is after it is in production.

**N0.4 — The schema is designed, not discovered.** Every table is born in a reviewed migration. Nothing
is created by an ORM on startup, in any profile.

## N1 — Identity

**N1.1 — Every table has a primary key.** Link tables included. Without one, duplicates fit, there is no
row identity for replication or change data capture, and the optimiser loses its cheapest access path.

**N1.2 — The key is a `UUID` in Java and `RAW(16)` in Oracle, and it is a UUID v7 generated by the
application.** Not a sequence: a correlative number leaks volume — a carrier receiving shipment 1041
knows the laboratory has shipped a thousand times. Not `SYS_GUID()`: a random UUID scatters inserts
across the whole index and every insert dirties a different block. **v7 carries its timestamp in the
high bits**, so keys generated in sequence land in the same region of the index, and reading a time
range reads consecutive blocks.

`RAW(16)` and not `VARCHAR2(36)`: sixteen bytes against thirty-six, on every primary key, every foreign
key and every index that includes one. The full reasoning is
[ADR-002](../docs/adr/ADR-002-uuid-v7-raw16.md).

**N1.3 — The primary key of a link table is the pair of linked columns.** The link *is* the pair. A
synthetic id on top admits two identical rows with different ids, and then "who has this role" has two
answers.

**N1.4 — No identity column is nullable.** A link with one end null is a link to nothing.

## N2 — References

**N2.1 — A reference inside the same module carries a foreign key.** Without it an orphan row is
representable, and the code reading it later cannot tell "does not exist" from "exists and is broken".

**N2.2 — A reference that crosses a module does not carry a foreign key.** It is a `UUID` column and
nothing else ([ADR-006](../docs/adr/ADR-006-modules-and-events.md)). A foreign key across the boundary
would make two modules share a physical dependency that neither declared, and the module model would be
a fiction at the database level.

The one deliberate exception is `ORGANIZATION_ID`, and it is deliberate because tenancy is the security
property of the product: there, declarative integrity beats decoupling.

**N2.3 — Every foreign key leads an index on its child column.** Oracle locks or scans the child table
when the parent row changes if the index is missing. It is the single most common performance defect in
a schema that otherwise looks correct.

**N2.4 — The delete action is explicit on every foreign key.** Cascade when the child cannot exist
without the parent — a shipment line without its shipment is nothing. Restrict when the child has a life
of its own. There is no default by omission: it is decided, per key.

## N3 — Tenancy

**N3.1 — Every table holding organization data carries `ORGANIZATION_ID NOT NULL`, with a foreign key.**
This is the column the whole security model rests on. Nullable, it would mean "belongs to nobody", and
a row belonging to nobody is a row everybody can see.

**N3.2 — `ORGANIZATION_ID` leads an index** on every table queried by organization. Every listing in the
product filters by it, so it is the first column of the access path, not an afterthought inside a
composite index.

**N3.3 — A global catalogue table declares itself as such and carries no `ORGANIZATION_ID`.** The
declaration exists so that "has no tenancy" can never quietly mean "we forgot it".

**N3.4 — Tenant filtering is proven with data.** A structural test says a predicate is written somewhere.
Only a test that inserts two organizations and asks as one of them proves the other's rows do not come
back.

## N4 — Types

**N4.1 — A quantity that is summed or compared is `NUMBER(p,s)`.** Never a floating-point type: a
temperature that must be compared against a threshold, and durations that are accumulated over a whole
journey, cannot carry binary rounding. `BINARY_DOUBLE` is fast and wrong for this.

**N4.2 — Precision and scale are decided per magnitude, not inherited.** A temperature is
`NUMBER(5,2)` — hundredths of a degree is what a probe reports. Coordinates are `NUMBER(9,6)`, which is
about ten centimetres. A percentage is `NUMBER(5,2)`. Copying `NUMBER(38,2)` everywhere is how a
traceability system loses the gram.

**N4.3 — An instant is `TIMESTAMP WITH TIME ZONE`, and `Instant` in Java.** A cold-chain shipment crosses
borders by definition; a timestamp without a zone is ambiguous the moment it does, and twice a year it is
ambiguous without going anywhere.

Note the trap that comes with it: `TRUNC(measured_at,'MI')` turns the `TIMESTAMP` into a `DATE` and takes
the fractional seconds with it. The downsampling query casts explicitly.

**N4.4 — A boolean is `NUMBER(1)` with `CHECK (col IN (0,1))`.** Oracle 23ai does have a native
`BOOLEAN`, and this project does not use it. A function-based unique index whose expression touches a
native `BOOLEAN` column materialises hidden virtual columns and freezes the table against schema change:
measured on Oracle 23.26, dropping that index, dropping a column of that table, or reclaiming unused
columns all answered `ORA-00600` — an internal engine error — with `SET UNUSED` as the only way out and
no way back.

This schema leans on function-based unique indexes in three places (N7.3). None of the three touches a
boolean today; `HAS_OPEN_EXCURSION` is the obvious future candidate. A type rule is worth having before
somebody needs it, and Hibernate maps `NUMBER(1)` to a Java `boolean` anyway, so what it costs is the
type name in the data dictionary.

**N4.5 — Text is sized by its content**, and `CLOB` and `JSON` never enter an equality predicate, a
`DISTINCT` or a `GROUP BY`. Oracle answers `ORA-22848`, and it answers at runtime — the code compiles,
the test that does not exercise that path passes, and it fails in front of a user. `threshold_snapshot`
and `detail` are read by key only.

The other half of this rule: **in Oracle the empty string *is* `NULL`**. A mandatory text column carries
`NOT NULL` **and** `CHECK (TRIM(col) IS NOT NULL)`, because `NOT NULL` alone lets `''` through as far as
the application is concerned.

## N5 — Lifecycle

**N5.1 — Soft delete has one name across the schema: `DELETED_AT`, and `NULL` means alive.** An instant
and not a flag, because the question after an incident is never only "is it deleted?" but "since when?".

`REVOKED_AT`, `DETACHED_AT` and `SUPERSEDED_AT` are **not** soft delete and must not be confused with it.
They close a window: a participant stops seeing a shipment, a device stops riding one, a certificate is
replaced by its next version. The row stays true about a period of time that really happened.

**N5.2 — "Deleted" and "enabled" are different concepts and do not share a column.** `DELETED_AT`
answers existence, `ACTIVE` answers whether it operates. Collapsing them is how a retired-but-historical
row becomes invisible to a report that needed it.

**N5.3 — Every table carries the four audit columns**: `CREATED_AT`, `CREATED_BY`, `UPDATED_AT`,
`UPDATED_BY`. The first two are `NOT NULL`. This is the floor; the `AUDIT_ENTRY` table is a different
thing — it records what was done, not when a row last changed.

**N5.4 — An entity declaring a restriction over a column maps that column.** If Hibernate filters on
`DELETED_AT` and the entity does not map it, the generated table has no such column and every `SELECT`
dies with `ORA-00904`.

## N6 — Indexes

**N6.1 — Anything queried by a criterion other than its primary key has an index for that criterion.**

**N6.2 — The column order of a composite index is decided by the predicate**: equalities first, range
last. `(shipment_id, measured_at)` serves "the readings of this shipment between these two instants";
the reverse order serves nothing.

**N6.3 — A unique index over a table with soft delete or with a state-scoped rule is partial**, and in
Oracle that means a function-based index:

```sql
CREATE UNIQUE INDEX UQ_HANDOFF_PENDING
  ON HANDOFF_REQUEST (CASE WHEN STATUS = 'PENDING' THEN SHIPMENT_ID END);
```

Rows that do not match the condition evaluate to `NULL`, Oracle does not index `NULL`s, and they drop
out of the index by themselves. A plain `UNIQUE` would also cover the closed rows and burn the value
forever — a rejected handoff would block the shipment from ever having another one.

It is the mechanism behind three guarantees of the product: one active assignment per device, one
pending handoff per shipment, one current certificate version per shipment.

**N6.4 — No index without a query that justifies it.** Every index is paid on every write.

## N7 — Constraints

**N7.1 — `NOT NULL` by default.** Nullable is the exception and means "this value may legitimately not
exist", never "sometimes we do not have it".

**N7.2 — A closed, stable set of values is a `CHECK`; a set the business administers is a catalogue
table with a foreign key.** The criterion is who changes it: a deployment or a screen. `PASS` /
`PASS_WITH_DEVIATION` / `FAIL` is a `CHECK` — it changes when the code changes.

**N7.3 — Every business uniqueness rule exists as a constraint in the database, even when the code
already validates it.** The code validates to give a decent error message; the database guarantees.
Without the constraint, two concurrent requests pass both validations and both write, and no test that
runs requests one at a time will ever catch it.

**N7.4 — No constraint or index carries a system-generated name.** A `SYS_C0015138` does not say what it
guarantees, so an integrity failure in production is not diagnosed — it is investigated. The canon is
`PK_<TABLE>`, `FK_<CHILD>_<PARENT>`, `UQ_<TABLE>_<COLUMNS>`, `IX_<TABLE>_<COLUMNS>`,
`CK_<TABLE>_<WHAT>`, and it is what makes the adapter able to turn a violation into a domain error by
reading the name ([ADR-007](../docs/adr/ADR-007-hexagonal-module-internals.md), rule 6).

## N8 — Naming

**N8.1 — Table names are `UPPER_SNAKE_CASE` and singular.** A row is one thing, not many.

**N8.2 — A reference column is named after its target: `<TARGET_TABLE>_ID`.** `SHIPMENT_ID`, not
`SHIPMENT` and not `ID_SHIPMENT`.

**N8.3 — The same concept is named the same everywhere.** If it is `MEASURED_AT` in one table it is not
`READ_AT` in another.

---

## N9 — Growth

**N9.1 — The table that grows without a ceiling is partitioned.** `TEMPERATURE_READING` is range
partitioned with a monthly interval on `MEASURED_AT`. Oracle creates each partition on its own as data
arrives, and it is included in the Free edition.

It is the only table in the schema with no natural ceiling: every other one grows with the number of
shipments, and this one grows with the number of shipments times their duration times the sampling rate.

**N9.2 — The Free edition ceiling is a design input, not a surprise.** 12 GB of user data and 2 GB of
RAM. The demo series generator works inside that ceiling on purpose, and the partitioning is what makes
dropping a month a metadata operation rather than a mass delete.
